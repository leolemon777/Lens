# ADR-001：Lens Windows 技术栈与部署

- 日期：2026-09-09
- 状态：已接受（v2.0 技术栈重规划：后端 Rust、桌面宿主 Tauri 2、UI React + TypeScript + Vite；旧 C#/WinUI 3 正式路线已被替代，历史 C++/C# 原型证据仅作迁移对照，不构成新栈验收）
- 上位文档：[Windows SPEC PLAN](../Lens-Windows-SPEC-PLAN.md)、[Windows CODE PLAN](../Lens-Windows-CODE-PLAN.md)

## v2.0 技术决定（2026-09-09）

用户决定放弃 WinForms/WinUI 正式界面路线，改为现代 Web UI 桌面方案，后端全面迁入 Rust：

| 层 | 选型 | 说明 |
|---|---|---|
| 桌面宿主 | Tauri 2（Rust） | 生命周期、窗口、单实例、托盘、原生对话框、命令入口；Windows 使用 WebView2 |
| UI | React + TypeScript + Vite | 前端编译为本地静态资源，生产包不依赖 Node.js 服务、远程网页或登录 |
| 业务后端 | Rust | 项目、索引、任务、编辑计划、模型管理、导出调度、诊断均迁入 Rust crate |
| Windows 平台 | Rust + `windows` crate | WGC、D3D11、Media Foundation、WASAPI、剪贴板、热键、DPI 用 Rust 实现 |
| 隔离工作进程 | Rust `lens-worker` | 继续兼容既有 stdio 协议 v1 |

边界：系统 DLL、图形驱动、FFmpeg 和识别引擎等外部原生依赖允许存在但须列入清单；旧自有 C++ 媒体 DLL 仅可用于迁移对照/临时实验，最终默认构建不得依赖它或 C# worker。若某项 Rust 平台能力无法通过原型验证，阶段保持未通过并记录缺口，不静默恢复旧技术栈。产品需求与质量指标不变，详见 CODE PLAN v2.0。

## 决策

| 领域 | 选定方案 | 证据 |
|---|---|---|
| 捕获 | Windows Graphics Capture + D3D11 | CaptureProbe 实测：4K 帧、PNG 落盘、与显示器物理像素一致 |
| 编码 | Media Foundation H.264 硬件编码（NVIDIA） | 60 秒 4K 19.42fps，GPU 路径无 CPU 拷贝 |
| 音频采集 | WASAPI 共享模式 loopback + 麦克风 | 60 秒双轨独立 WAV，48kHz 2ch 16-bit |
| 可恢复分片 | 5 秒独立 MP4 + manifest 索引 | 强退测试：confirmed 分片 100% 可解码，损失 ≤5 秒 |
| DPI 感知 | Per-Monitor DPI V2 | ShellProbe 实测：显示器枚举与 WGC 捕获一致（3840x2160） |
| 窗口/托盘 | Tauri 2（Rust）+ 必要的 Win32 集成 | 待 M0 Tauri 原型验证托盘、热键、选区、置顶、透明窗口、混合 DPI、负坐标、焦点恢复、捕获排除与 E 盘部署；ShellProbe 的 Win32 结论仅作对照 |
| UI 框架 | React + TypeScript + Vite（WebView2 渲染） | 待 M1 建立工程与锁文件 |
| 核心规则 | Rust 业务后端 + `lens-worker` | rust-toolchain.toml 已锁 1.98.1；现有 crate 为迁移基线 |

## 编码器实测

| 编码器 | 类型 | 实测表现 |
|---|---|---|
| NVIDIA H.264 Encoder MFT | 硬件 | 4K 60 秒录制 19.42fps，16Mbps，全程 GPU 路径（MF_SINK_WRITER_D3D_MANAGER + DXGI Surface Buffer，无 CPU 像素拷贝） |

帧率缺口：目标 30fps，4K 实测 19.42fps。可能瓶颈：4K H.264 编码吞吐上限或 WGC 帧池节奏。后续需对比 1080p/1440p 表现归因。在 60fps 目标场景（SPEC G-W2）可能需要降低编码分辨率或启用 NVIDIA 专用编码预设。

## 音频架构决定

原计划：系统声和麦克风作为 MP4 内 AAC 轨。实测发现 `MF_SINK_WRITER_D3D_MANAGER`（视频硬编必需）与 AAC 音频流在同一 sink writer 中死锁。改为：

1. MP4 只含视频轨
2. 系统声和麦克风各自独立 WAV 文件（48kHz 2ch 16-bit PCM）

理由：
- 与 macOS 版一致（独立音频资产）
- 满足"独立可检查轨道"要求
- 避开 D3D 管理器与 AAC 的兼容性问题
- 后续 W4 合成阶段再统一混流

风险：多文件素材需要项目格式明确支持多资产引用；用户可能期望单个 MP4 文件。在 W2 内测时根据用户反馈决定是否投入混流。

## 分片与恢复

选型：5 秒独立 MP4 分片 + JSON manifest 索引。

实测证据：
- 正常录制：3 片各自独立可解码（Shell 识别 5s/4s/2s 时长）
- 强退（第 12 秒杀进程）：seg-0 和 seg-1 confirmed 且可解码，seg-2 writing 且不可解码（无 moov atom）
- 损失边界：≤5 秒（当前正在写的分片）

限制：恢复扫描目前只检查 manifest 和文件存在性，不做实际解码验证；正式版需要在恢复时用 Media Foundation 逐片解码确认。

## DPI 与坐标

**硬性决定**：进程入口最先调用 `SetProcessDpiAwarenessContext(DPI_AWARENESS_CONTEXT_PER_MONITOR_AWARE_V2)`，在任何显示器/窗口 API 之前。

证据：

| 模式 | 显示器报告 | WGC 捕获 |
|---|---|---|
| 非 DPI 感知 | 2560x1440（虚拟化） | 3840x2160 |
| **DPI V2** | **3840x2160** | **3840x2160** |

未设置 DPI V2 时坐标系统分裂成两套，选区、窗口、捕获无法对齐。

## 部署

### v2.0 目标形态（Tauri）

- Tauri NSIS EXE 安装器，支持自选安装目录；WebView2 存在性与离线部署策略在 M0 冻结。
- 发布包含 Rust/Tauri 应用、worker、静态 UI、许可证、符号、SHA-256 与机器可读 release.json；不包含旧 WinForms/C# 产品 DLL，不要求安装 .NET 应用运行时。
- Authenticode 与更新包签名分别校验；安装、升级、回滚、卸载保留素材按 G-W6 验收。

### 旧 C++ 探针部署结论（仅历史对照）

### 当前探针（Debug）

依赖：MSVCP140D, VCRUNTIME140D, ucrtbased（调试 CRT，干净机器无）

### Release 构建

依赖：MSVCP140, VCRUNTIME140, VCRUNTIME140_1 + UCRT API sets + 系统 DLL（D3D11, MFPlat, MFReadWrite 等）

结论：Release + `/MT`（静态 CRT）可实现单 exe 零外部依赖部署。正式版建议 `/MT` 避免要求用户安装 VC++ Redistributable。

### 已知原型限制

探针输出路径硬编码到仓库目录，正式版需改为配置或相对路径。在 E:\LensProbeTest 部署测试确认：exe 可从任意位置运行，但输出仍写入仓库路径。

### OCR 实测结论（2026-09-09 AnalysisProbe）

**引擎**：Windows.Media.Ocr（Windows 10+ 内置，零部署成本）

| 语言 | 可用性 | 英文识别 | 中文识别 | 速度 |
|---|---|---|---|---|
| en-US | ✓（用户默认） | 良好（完整句子、字母、数字） | 完全不识别 | 23-26ms |
| zh-Hans-CN | ✓（需中文语言包） | 良好（与 en-US 相当） | **空输出**（中文行返回空字符串） | 63ms |

测试条件：GDI+ 渲染的 Microsoft YaHei 32px 干净文本图（1920x640，白底黑字），中英混合 5 行。

**结论**：Windows.Media.Ocr 的中文识别在干净合成图上不可靠——zh-Hans-CN 引擎对中文行返回空字符串。英文识别良好且速度快（<30ms）。**不建议以 Windows.Media.Ocr 作为中文 OCR 的唯一引擎**。

候选替代方案（未实测）：
- PaddleOCR：中文质量高，模型体积约 10-100MB，Apache 2.0 许可证
- Tesseract + chi_sim：经典方案，速度较慢，AGPL 许可证需评估
- Windows.Media.Ocr 作为英文快速路径 + PaddleOCR 作为中文路径的混合方案

最终选型需要 AnalysisProbe 对 PaddleOCR/Tesseract 做同样的合成图实测后决定。

## 未选方案与理由

| 方案 | 未选理由 |
|---|---|
| DXGI Desktop Duplication | 无法指定单窗口捕获；权限要求更高；WGC 是官方推荐路径 |
| FFmpeg 外部进程 | 增加部署体积和进程管理复杂度；MF 硬编路径已验证可行 |
| MP4 内混 AAC 音轨 | 与 D3D 管理器死锁（实测）；独立文件更符合"独立可检查"要求 |
| 单文件连续 MP4 | 无法满足 ≤5 秒恢复粒度；分片方案已验证 |
| Windows Forms / WPF | 不满足 SPEC 的现代 Windows 体验要求 |
| WinUI 3 / C# 正式界面 | v2.0 用户决定改用 Tauri 2 + React/TypeScript + Rust；旧选型不再扩展 |
