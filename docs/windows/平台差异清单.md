# Lens Windows 平台差异清单

- 日期：2026-09-09
- 基线 commit：`e1756ad6b1b335f8a390ea4929cb8fd6f0718b43`
- 状态：基于当前源码静态盘点；带"待实测"的项目在 W0 原型中验证后补充证据。

## 1. LensCore 依赖盘点

`Sources/LensCore` 共 37 个 Swift 文件。依赖面非常干净，这是跨平台移植的有利条件：

| 类别 | 文件 | Windows 对策 |
|---|---|---|
| 仅 `import Foundation` | 35 个文件 | 纯数据结构与 JSON 逻辑，Rust 逐项移植，用 Swift 黄金测试对齐 |
| `import CoreGraphics` | `CaptureGeometry.swift`（CGRect/CGSize/CGPoint） | Rust 侧定义等价矩形类型并实现 `standardized`（负宽高归一化）语义 |
| `import Darwin` / `import Glibc` | `CoreWorkerRuntime.swift`（条件编译，进程 spawn/pipe） | Windows 由 Rust `lens-worker` / 宿主进程管理承担；不再使用 C# `CoreWorkerClient` |

`Sources/LensMac` 大量使用 AppKit、SwiftUI、ScreenCaptureKit、AVFoundation、Vision、Speech，全部不可复用，只能作为行为规范参考；对应 Windows 实现按 CODE PLAN 步骤 3-8 新写。

## 2. windowID / displayID：UInt32 装不下 HWND

现有可移植文档中的标识符类型：

- `LensManifest.ScreenshotCaptureSource.windowID: UInt32?`、`displayID: UInt32?`
- `LensManifest.RecordingCaptureSource.windowIDs: [UInt32]`、`displayID: UInt32?`
- `CaptureEvents` 多处 `displayID: UInt32?`
- `ScrollingCapturePlan.displayID: UInt32`

macOS 的 CGWindowID 是 UInt32，恰好能存；Windows 的 HWND 是指针宽度（64 位进程下 64 位），直接截断必然碰撞。**处理决定**（与 SPEC 第 5.4 条一致）：

1. 运行时捕获一律用原生 `HWND`/`Microsoft.Graphics.Capture.GraphicsCaptureItem` 句柄，不进入持久化 JSON。
2. 持久化来源描述如需 Windows 窗口身份，新增独立平台字段（例如窗口标题 + 进程名 + 应用用户模型 ID 的稳定摘要），schema 升级后双端同步，禁止把 HWND 塞进现有 UInt32 字段。
3. 读取旧 macOS 项目时 UInt32 原样保留展示，不解释为 Windows 句柄。

## 3. 媒体格式：CAF / MOV 硬编码

源码事实（`Sources/LensCore/LensProjectStore.swift`、`Sources/LensMac/Capture/ScreenRecordingService.swift`）：

- 麦克风轨固定写 `raw/microphone.caf`
- 摄像头轨固定写 `raw/camera.mov`
- 录制分段文件为 `microphone-NNN.caf`、`camera-NNN.mov`
- 屏幕轨由 `ScreenVideoTrackWriter` 写 MOV（`fileType: .mov`）

Windows 处理决定：

1. **读旧项目**：W0 需实测 Windows Media Foundation + 系统补丁对 Core Audio Format（本质是 AIFF 系容器）和 ProRes/H.264 MOV 的实际解码能力；不能假设能读，也不能假设完全不能读。结论写入 ADR-001。
2. **写新项目**：Windows 首选 MP4（H.264/AAC），麦克风独立轨可用 M4A/WAV；任何新格式必须先补 macOS 读取测试再启用写入（SPEC 第 5.5 条）。
3. 路径角色（`LensAsset.role` + `relativePath`）保持，容器差异不改变项目结构。

## 4. 路径与文件系统语义

现状：`LensProjectStore`、`LensLibraryPersistentIndex` 使用 `URL.appendingPathComponent`、`standardizedFileURL`、`resolvingSymlinksInPath`、`pathComponents` 做包内相对路径安全校验（`safeAssetURL`）。

Windows 需要补齐的差异：

| 差异 | 风险 | 对策 |
|---|---|---|
| 大小写不敏感（NTFS 默认） | `raw/a.png` 与 `raw/A.PNG` 判重失败、保存时静默覆盖 | Rust 侧路径规范化统一小写比较；写入前枚举实际目录做大小写冲突检测 |
| 反斜杠与正斜杠混用 | JSON 里的 `/` 在 Win32 API 变 `\`，往返后字节漂移 | 项目内统一 `/`，仅在打开文件瞬间转换为 OS 路径 |
| 盘符与绝对路径 | `E:\x`、`\\server\share` 可能穿透包根 | 拒绝绝对路径、UNC、盘符前缀、`..`，解析后再查 junction/symlink/reparse point |
| Windows 保留名 | `CON`、`PRN`、`AUX`、`NUL`、`COM1`… 无法落盘 | 文件名规范化时拒绝保留名（含带扩展名的 `CON.txt`） |
| 备用数据流（ADS） | `file.png:stream` 可能写到流里 | 拒绝包含 `:` 的文件名（盘符前缀已单独处理） |
| 长路径 | 260 字符限制（未开 LongPathsPolicy 时） | 首版用 `\\?\` 前缀 API 或限制路径长度并给出明确错误 |

这些规则集中实现在 Rust `project.rs` 的路径策略层，C# 侧不做第二套解释。

## 5. Schema 与协议基线

- 项目 schema：8 个可移植文档（manifest、edit-plan、screenshot-edit、segments、scrolling-capture、ocr、transcript、insights）；manifest 当前版本 `0.9`，最低可读 `0.1`，版本号为 `major.minor` 两段式。
- Worker 协议：v1，4 字节大端长度前缀，帧上限 1 MiB（1,048,576 字节），requestID 为 UUID，省略空值语义需逐字段对齐。
- 黄金样本已在仓库：`Tests/LensCoreTests/Fixtures/core-worker-protocol-v1-golden.json`、`LegacyRecordingV0_1`、`LegacyScreenshotV0_1`。Rust 测试直接读这些文件，不建副本。
- 错误文案目前是中文字符串（`LensSchemaCompatibilityError`），Rust 侧应保留错误码结构，用户可见文案在应用层本地化，避免核心库绑死单一语言。

## 6. 坐标与 DPI

- `CaptureGeometry` 基于 CGRect，`standardized` 处理负宽高；Rust 移植时需实现等价归一化。
- macOS 全局坐标（CGWindowList）与 Windows 桌面物理像素/每显示器 DPI 感知 V2 语义不同；负坐标显示器、混合缩放在 CODE PLAN 步骤 2 的 ShellProbe 中实测。
- 事件颜色用十六进制字符串（`UInt32(trimmed, radix:16)` 校验 6 位），不依赖 NSColor，可直接移植。

## 8. 已确认：DPI 虚拟化与显示器分辨率（2026-09-09 ShellProbe 实测）

ShellProbe 以 `DPI_AWARENESS_CONTEXT_PER_MONITOR_AWARE_V2` 启动后，`EnumDisplayMonitors` 报告 DISPLAY1 为 **3840x2160**（DPI=96，100%），与 WGC 捕获纹理完全一致。此前 CaptureProbe 报告 2560x1440 是因为在设置 DPI 感知之前枚举了显示器，触发了 DPI 虚拟化。Windows 版应用必须在任何显示器/窗口 API 调用前设置 Per-Monitor V2，否则坐标系统会分裂成两套。
- Rust stable-msvc 与 VS 17.14 工具集、SDK 26100 的实际配合版本（安装后冻结）。
