# Lens 架构梳理与双端对齐基线

日期：2026-09-10。依据当前工作区源码；Windows 目录存在未跟踪文件，因此本报告对应工作区，不仅对应 Git HEAD。

用户目标：Windows 完整复现现有 Mac 产品的功能、主要交互、视觉风格、编辑结果和可靠性。系统快捷键、权限入口等使用 Windows 等价实现，不能以平台差异为理由省略产品能力。

本轮完成架构、主要调用链与关键差异静态核查，以及现有基础测试。未修改产品源码，未执行截图录屏真机矩阵或视觉对照，不将已有界面、测试数量和历史探针日志当作功能等价证据。

## 1. 总体结构

仓库是双端同仓、两套实现。Mac 使用 Swift 6 / Swift Package Manager，最低 macOS 15；Windows 使用 Tauri 2、React、TypeScript、Vite 和 Rust。当前并非两端共用同一个业务运行时。

| 目录或模块 | 职责 | 主要联系 |
|---|---|---|
| `Sources/LensCore` | 项目格式、文件存储、素材库与索引、事件、时间线、自动运镜、光标、字幕、标注、整理、恢复规则、worker 协议 | 被 `LensMac` 调用，是 Windows 行为移植的主要参考 |
| `Sources/LensMac/UI` | AppKit 窗口控制器、SwiftUI 页面、编辑器模型与播放控制 | 通过模型和回调触发采集、项目读写和渲染 |
| `Sources/LensMac/Capture` | 系统采集、多轨音视频、OCR、转写、图像和视频渲染、恢复 | 使用 Apple 框架，消费 `LensCore` 的数据与计划 |
| `Sources/LensMac/Support` | 偏好、权限、热键、诊断、启动健康、剪贴板等 | `AppDelegate` 组织这些服务与 UI |
| `Desktop/src` | React 页面、选区、录制条、截图与视频编辑器 | 经 `bridge/commands.ts` 调用 Tauri 命令 |
| `Desktop/src-tauri/src/lib.rs` | Windows 生命周期、托盘、热键、多窗口、共享状态、命令与后处理调度 | 直接链接三个 Rust 库；当前承担较多业务编排 |
| `CoreRust/crates/lens-core` | Rust 项目模型、schema、路径策略、部分编辑与整理规则、协议 | 被项目服务、Windows 平台和宿主使用；尚非 Swift 核心的完整移植 |
| `CoreRust/crates/lens-project` | 项目包创建、扫描、保存、媒体检查与 FFmpeg 后处理 | 使用 `lens-core`；由宿主调度 |
| `CoreRust/crates/lens-platform-windows` | Win32/WinRT、WGC、D3D11、Media Foundation、WASAPI、DPI、剪贴板、OCR等 | 向宿主提供原生能力，依赖 `lens-core` |
| `CoreRust/crates/lens-worker` | stdio 协议原型 | 当前只处理一次握手然后退出；不是正式后台任务引擎 |
| `Tests` / Rust tests / `Desktop/tests` | Mac 测试、跨语言黄金样本、Rust 测试与少量前端检查 | 基础测试与真实设备、媒体、视觉验收须分别统计 |
| `Scripts/windows` | 检查环境、构建、运行、测试、打包 | 当前产品入口为 Tauri/Rust；旧 C#/WinForms 路线已退出 |

Windows 前端依赖清单声明 React 19.3、TypeScript 5.9、Vite 8.2，Tauri Rust 依赖声明 2.11.5；这些是仓库声明，不是对外部最新版本的判断。

## 2. Mac 主链路

`main.swift → AppDelegate → AppModel / 各 WindowController / CaptureCoordinator / ScreenRecordingService`。

- 截图：热键或操作中心 → `CaptureCoordinator` → 选区与来源选择 → `ScreenCaptureService` → `LensProjectStore` 保存 `.lens` → 剪贴板、Quick Access、贴图、素材库；OCR 与整理是后续分支。
- 录屏：来源与选项 → `ScreenRecordingService` → 屏幕、系统声、麦克风、摄像头、指针事件分别采集 → 分片和恢复状态 → 停止后的组装、处理、预览。
- 成片：原始媒体与事件 → `LensCore` 生成非破坏性计划 → `AutoPreviewRenderer`、音频混合、字幕、画中画等服务 → 可播放预览与导出。
- 编辑：截图/视频编辑器模型修改计划和时间线 → 对应渲染器重新生成派生结果；原始素材保留。
- 检索：项目、OCR、转写和整理结果 → 持久索引 → 素材库搜索；用户校正与自动分析分层保存。

Mac 的产品中枢是 `AppDelegate`；`LensCore` 也包含 Foundation 文件 I/O 等，并非只有纯计算。Windows 需要对齐的是完整行为和数据语义，不能只复制几个 JSON 结构。

## 3. Windows 主链路

`main.tsx → App.tsx（按 window 参数选择窗口页面）→ commands.ts → Tauri invoke → lib.rs → Rust 项目与平台模块`。

- 截图：选区坐标 → CSS/DPR 与桌面物理坐标映射 → 原生截图 → 剪贴板 → `.lens` → Quick Access / 素材库。
- 录屏：`start_recording_session → LiveRecording`，启动视频、音频、事件采集；视频使用 WGC/D3D11 与 Media Foundation，音频使用 WASAPI 独立 WAV。
- 停止：`finish_recording → finalize_recording_package → post_process_recording`，执行分片拼接、混音、转写尝试、计划与分析写入、恢复报告。
- 编辑：截图由 Canvas 渲染并保存计划和位图；视频保存时间线并调用 FFmpeg 生成片段和拼接结果。
- 素材库：`get_app_state → snapshot → scan_library`；当前页面定时刷新并扫描项目，尚不是 Mac 的完整增量持久索引体系。

实际生产路径主要在宿主进程内直接调用 Rust 库，没有经过 `lens-worker` 做完整工作进程隔离。

另外，宿主主动启动 Rust 本地 HTTP 服务查找磁盘 `dist`，再让 WebView2 导航至 `127.0.0.1`。因此当前部署不能仅按“标准 Tauri 内嵌资源”推断，需要核对该实际路径和发布包一致。

## 4. 跨端共享契约

核心资产是开放 `.lens` 目录包：`manifest.json` 描述项目，`raw/` 保留原始素材，`events/` 保存事件及分片信息，`edits/` 保存非破坏编辑，`analysis/` 保存识别和整理，`previews/` 保存派生结果。

两端已共享部分历史项目夹具和 worker 黄金帧。协议使用 4 字节大端长度前缀 JSON，帧上限 1 MiB。复用这些测试是良好基础，但目前旧项目兼容测试主要检查版本与路径，不能证明媒体可解码、编辑语义等价或 Mac → Windows → Mac 完整往返。

跨端对齐需覆盖：字段默认值、枚举、时间基准、坐标、资源角色、未知字段与未来版本、媒体容器、文件路径及写入规则。特别是 Windows HWND 不应直接作为 Mac UInt32 窗口标识持久化。

## 5. 已确认的重要差距

以下是代码可见事实和静态推断，尚未为每项执行运行时复现。

| 项目 | 当前源码证据 | 对完整 Windows 版的影响 |
|---|---|---|
| 普通视频导出 | `Desktop/src-tauri/src/lib.rs::export_video` 从 `raw/segments` 找到一个 MP4 后直接导出，没有消费完整时间线或全部分片 | 导出存在截断录制及丢失编辑效果的问题；应优先修复 |
| 预设不等价 | 同一函数把平衡/轻量缩放至 1920/1280 宽，轻量使用 H.264 | 与 Mac 文档所述保留源分辨率、帧率限制及轻量 HEVC 行为不同 |
| 变速同步 | `lens-project/src/post.rs::export_timeline` 变速只设置视频 `setpts`，未见音频对应变速过滤 | 无法认为音视频变速已同步 |
| 字幕与剪辑 | `render_edit` 仅向最后一个启用片段传入字幕文件，未做完整源时间映射 | 多片段字幕、裁切、重排与变速同步尚未对齐 |
| 自动运镜与效果 | 后处理生成 `edit-plan.json`，当前 `render_edit` 主要消费时间线和 VTT，未接入完整自动计划 | 有计划文件不代表实际成片有对应运镜、光标与画中画效果 |
| 摄像头 | `camera.rs` 仅枚举设备；宿主写入的报告也说明未接入独立摄像头分轨 | 缺真实摄像头采集、独立轨、编辑和合成闭环 |
| 本地转写 | `transcript.rs` 尝试 PATH 中的多个 Whisper 命令，失败后将能量分段写成“语音 1”等占位文本 | 占位文字不能当作真实转写或字幕；需明确失败状态和可用模型管理 |
| JPEG 保存 | 前端以 JPEG Data URL 调用 `saveAnnotation`，项目层仍固定保存为 `previews/annotated.png` | 格式和文件扩展名不一致，且还不是完整文件导出流程 |
| 工作进程 | `lens-worker/src/main.rs` 一次握手后退出 | 任务处理、取消、进度、故障隔离及重启恢复尚未完整接入 |
| 处理失败状态 | 停止后多处后处理和保存使用 `let _ = ...` 忽略结果 | 需要明确区分原始录制成功、成片失败和可重试状态 |
| 安装与依赖 | 后处理直接启动 PATH 中的 FFmpeg/ffprobe；前端服务查磁盘 dist；打包脚本主要复制 EXE/worker/NSIS | 当前未见完整资源与媒体依赖交付闭环，开发机可用不能证明干净机可用 |
| 测试入口 | `test.ps1 -Suite Protocol` 指向不存在的 `protocol_tests` target，实际测试名为 `protocol_golden` | 验收脚本本身需要校正，避免仅依赖 Unit 通过 |

截图工具已有多种标注、基本撤销重做和画布；视频编辑器已有分割、片段启停、顺序、速度、转场和字幕文字入口。但完整对象编辑、画布选项、视频标注、摄像头关键帧、未保存防护、权限设置、无障碍及交互手感仍需按 Mac 逐项建立对照，不能从页面存在推定完成。

## 6. 后续工作顺序

1. **固定产品对齐矩阵**：以 Mac 源码、测试和实际操作为基准，每项记录入口、操作、预览、文件结果、异常行为和验证证据。视觉对齐另做双端相同状态对照。
2. **先保障输出正确**：统一完整分片、编辑时间线、预览和导出的来源；修复音视频变速及字幕映射；让后处理失败可见且可恢复；移除伪转写结果。
3. **补齐截图与录屏闭环**：真实多屏/DPI、窗口跟随、滚动稳定、截图编辑与导出、侧轨选项、摄像头、暂停与强退恢复。
4. **补齐编辑与智能能力**：对齐 Swift 运镜、光标、点击反馈、背景、画中画、视频标注、字幕、音频处理、检索与人工校正。
5. **完成交付验收**：前端资源和离线媒体依赖随包交付；干净机安装、升级、卸载、签名与双端项目真实往返；补长时录制、故障、性能和无障碍矩阵。

继续现有 Tauri/React/Rust 路线，以 Mac 行为为标准逐步补齐。宿主的业务调度可随上述功能修复逐步抽出成服务，避免一次无必要的大规模重写。

## 7. 本轮验证

- 执行 `Scripts/windows/test.ps1 -Suite Unit` 成功：Rust 共 83 项通过、0 失败，8 项硬件测试忽略；TypeScript 类型检查通过。
- 首次调用在 20 秒工具超时前已完成 Rust 测试输出；随后重新执行整个 Unit 入口，得到退出码 0 和成功结尾。
- Unit 入口不包含完整 Tauri 宿主构建、前端交互测试或所有媒体验收。
- 本轮未在 Windows 上运行 Mac 测试，未进行真实捕获、摄像头、录制强杀、完整安装器或像素级界面对照。
- 现有文档含历史 C++/C# 探针记录及部分过时状态；后续以当前代码与可复现的新栈实测证据更新，不套用历史通过结论。
