# 功能代码改动计划——录屏停止与后处理体验（2026-08-29）

## 背景与目标

当前"停止录制 → 成片可用"链路存在三类体验损耗，本计划在不改变 `.lens` 项目格式、
不改变 `AutoEditPlan` 渲染语义的前提下消除它们：

1. **主线程卡顿**：停止/暂停路径上的分段拼接、麦克风 CAF 逐帧拼接、首段整文件复制
   全部在 `@MainActor` 上同步执行；长录屏停止时 UI 可能失去响应。
2. **第二次全片视频编码**：存在麦克风轨时，`previews/auto.mp4` 被特效渲染编码一次后，
   `AudioMixdownRenderer` 又用 `AVAssetExportSession` 把整段视频重新编码一次来挂混音，
   多一代有损 + 全片重编耗时。
3. **后处理占用主 actor**：`processRecording` 在 MainActor 上运行，并用
   while-sleep(120ms) 自旋做互斥。

## 阶段划分

> **进度（2026-08-29）**：P0、P1、P2、P3、P4 已完成并通过全量测试；
> P5（签名/更新通道）待做。

### P0 建立基线（约 0.5 天）✅

- 基线：`swift test` 558 项全绿（235s）。
- G2 时长分档基线（5/10/30 分钟 stop→可播放）需要真机屏幕录制权限，
  留待发版前在实机上补录；代码门槛回归以 G2 脚本现成的
  p95 主线程调度延迟 ≤50ms 判据为准。

### P1 停止路径出主线程（约 1–2 天）✅

实现记录：`RecordingSegmentAssembler` 由 `@MainActor final class` 直接改为
`actor`（类本就无状态，`assembleAudioSegments` 保持同步签名，调用方加 `await`）；
`archiveFirstSegmentsIfNeeded` 转为 async，三处整文件复制经 actor 新增的
`copyFileIfNeeded` 执行；原 `flatMap` 闭包因含 `await` 重构为先算局部路径再构造
`RecordingSegment`。`ScreenRecordingService` 对外 API 未变。

1. 新建 `SegmentAssemblyEngine`（`actor`，输入全部为 Sendable 值：分段索引、文件 URL、
   参数），把 `RecordingSegmentAssembler` 的四个重操作迁入：
   `assembleVideoSegments`、`assembleAudioSegments`、`muxSystemAudio`、
   `RecordingSegmentAssembler.swift:332` 处的 `copyItem` 归一化复制。
2. `ScreenRecordingService.finishActiveSegment` 内的 `AVURLAsset.load(.duration)`
   实测时长探测一并迁入 engine。
3. `ScreenRecordingService.archiveFirstSegmentsIfNeeded`（`:995`）的整文件复制迁入
   engine（或改用后台队列）。
4. `ScreenRecordingService` 保持 `@MainActor` 门面与现有对外 API 签名不变；内部
   `await` engine；UI 回调（状态/进度）照旧 hop 回 Main。
5. `RecordingSegmentAssembler` 保留为薄封装或直接删除，按调用点数量定。

**测试**：
- 现有 `RecordingSegmentAssembler` 相关测试迁到 engine（输入本就是纯值，改动小）。
- G2 的 p95 主线程调度延迟 ≤50ms 门槛作为"停止期间主线程可响应"的回归判据。

**风险**：SCStream 回调时序与 writer 逻辑一律不动，只动"停止后的装配"；
`stop()` 对外仍返回 `SavedLens`，失败语义不变。

### P2 后处理出主线程 + 去自旋（约 1 天）✅（部分）

实现记录：新增 `Support/RecordingProcessingGate.swift`（per-package 续航式门，
release 直接把钥匙交给队首等待者），`processRecording` 的 120ms 自旋移除；
配套 `RecordingProcessingGateTests` 锁定"同包串行保序、异包并发"。
`processRecording` 本体仍留在 MainActor（渲染器去隔离涉及光标资产，按上文
风险提示单独处理），自删"顺带收窄 AutoPreviewRenderer"为后续独立改动。

1. 新建 `RecordingPostProcessor`（`actor`），承接 `processRecording` 的主体：
   loadAutoEditPlan → previewRenderer.render → 混音 → 效果验证 → 健康报告写盘。
   `LensProjectStore` 与各 renderer 均为值语义/Sendable，可安全离开 MainActor。
2. `processingRecordingPackages` 自旋互斥改为 actor 天然串行；多个录屏仍保持串行
   处理（与转写串行队列约束一致），但不再占用 MainActor。
3. AppDelegate 保留：入口调度、完成/失败回调 hop 回 Main、UI 状态更新。
4. 顺带把 `AutoPreviewRenderer` 的 `@MainActor` 收窄为非隔离——注意：它缓存
   `CursorRenderAssets`（系统光标图，构建疑似涉及 AppKit，`AutoPreviewRenderer.swift:30-36`），
   收窄方案应为"光标资产在主线程预取后以值传入 actor"，而非简单去掉注解。

**测试**：全量 `swift test`（`RenderedPreviewExportGateTests`、
`AutoPreviewRendererTests` 必须全绿）。

### P3 消灭第二次视频编码（约 2–3 天，收益最大）✅

实现记录：
- `AudioMixdownRenderer` 抽取 `preparedMicrophone`（条件化 + 时间线映射）与
  `systemAudioParameters`（LUFS + ducking 包络）两个共享助手，旧两遍路径
  `renderWithReport` 行为不变（原测试全绿证明等价）；
- 新入口 `prepareMixedAudioSidecar`：麦克风/系统声（含转场扁平化）经
  `AVAssetReaderAudioMixOutput`（读取时应用 audioMix）+ 复用
  `AudioSampleBufferPCMConverter` 离线混成 **PCM CAF** sidecar——无中间 AAC 代；
- `AutoPreviewRenderer.render` 新增 `mixedAudioURL`：特效渲染的同一遍视频编码里，
  经 `assetByReplacingAudio`（composition 换轨）嵌入 sidecar；画中画路径经
  `PresenterCameraRenderer` 的 `mixedAudioURL` 参数取同一音轨源；
- `processRecording`：sidecar 准备失败自动回退旧两遍路径（`renderWithReport`
  原样保留），成功则单遍出片；
- 调试中发现并修复一个 AVFoundation 生命周期陷阱：`insertTimeRange(of:)` 要求
  源轨道的 `AVURLAsset` 在插入期间存活，条件表达式里创建的临时 asset 释放后
  插入报 -11800/-12780（helper 内已留注释）；
- 回归测试 `testSinglePassSidecarEmbedsMicrophoneMixDuringTheOnlyVideoEncode`：
  锁定 60 FPS 保真、成片音轨存在、混音电平证据三件事。

现状：视频被编码两遍（特效一遍 + 混音挂载一遍）。触发条件（已核实
`AudioMixdownRenderer.requiresMixdown`，`AudioMixdownRenderer.swift:350-357`）：
`plan.isEnabled && (microphoneURL != nil || systemVolume ≠ 1)`——即**有麦克风，
或用户调整过系统音量（哪怕没有麦克风）**都会走第二遍全片重编码；导出 preset 为
`AVAssetExportPresetHighestQuality`（`VideoExportProfile.swift:18,22`）且挂载
videoComposition，passthrough 在此路径上不可能发生。

1. **拆分** `AudioMixdownRenderer` 为两段：
   - `AudioMixdownPreparer`：只产音频。VoiceAudioProcessor 条件化麦克风（已有）
     → 转场时间轴映射（`VideoTimelineCompositionBuilder` 已有 `includesVideo: false`
     分支）→ NarrationActivityAnalyzer 语音区间 → ducking/系统声音量/LUFS 包络
     **离线渲染**成单一音频 sidecar（AVAssetReader + AVAudioFile 逐块混写，
     替代现在的 `AVMutableAudioMix` 运行时参数）。
   - 旧 `render` 保留为 fallback 路径。
2. **单遍编码**：`AutoPreviewRenderer.render` 增加可选 `mixedAudioURL` 参数；
   writer 会话中以 AVAssetReader 读取 sidecar 写入音频轨，视频特效一次编码成型。
3. processRecording 改为：先 Preparer 产 sidecar → 单遍渲染 → 验证；
   Preparer 失败时回退旧两遍路径（对齐现有 `voiceProcessingFellBack` 模式）。

**前置确认**：AutoPreviewRenderer 当前携带系统声的 passthrough 分支实现方式
（决定 sidecar 时间基以合并后 `screen.mp4` 为准，与现 mixdown 输入一致）。

**验收**：
- 新旧路径输出经 `AudioMediaEvidenceAnalyzer` 对比：RMS 差异在现有容差内、
  音画时长漂移 ≤0.15s；
- `RenderedEffectVerifier` 全绿；60 FPS 保持（把
  `timingPreservingVideoComposition` 的 30 FPS 教训写成新路径的回归测试）；
- G2 音画漂移 ≤0.25s。

**风险**：AVAssetWriter 音轨与视频 PTS 对齐；缓解：sidecar 以成片时间基离线渲染，
时长以音频为准裁齐（复用现有越界过滤/裁齐逻辑）。

### P4 快赢修复（约 0.5–1 天，可与 P2 并行）✅（1、2 完成）

实现记录：`CaptureCoordinator.showError` 的 `NSAlert.runModal` 替换为
`onCaptureFailed` 回调，AppDelegate 接 toast（不再抢焦点）；`stopCapture`
捕获 `SystemAudioTrackWriterError.noSamples` 后继续完成停止，缺失的系统声轨
由既有的 `requestedMediaTrackMissing` 健康警告上报（`.systemAudio` 资产在
`beginRecording` 即声明，零样本时 integrity 检查自动命中）。

1. 截图/捕获失败弹窗 `runModal`（`CaptureCoordinator.swift:740-747`）→ 复用
   `ToastWindowController`，非阻塞。
2. `SystemAudioTrackWriter.finish()` 零样本抛错（`SystemAudioTrackWriter.swift:156-158`）
   → `stop()` 捕获该错误降级为"系统声轨缺失"警告 + `storage`/`audio` 诊断事件，
   不让无输出设备的"录系统声"会话整体失败（对齐
   `RecordingOptionalTrackAvailability` 的可选轨降级模式）。
3. （可选）窗口消失检测 1.5s 轮询 `SCShareableContent`
   （`ScreenRecordingService.swift:1194-1231`）降频或迁后台队列。

## 明确不做的事

- 不改 `.lens` 项目 schema 与 `AutoEditPlan` 渲染语义（零迁移成本、验证器行为不变）；
- 不在本轮拆解 `AppDelegate` / `LensProjectStore` 巨型文件（与体验无直接因果，
  另立重构轮次，避免与性能改动互相污染 diff）。
