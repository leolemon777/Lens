>   `CaptureOverlayWindow` 确认无任何屏幕像素缓存（透明窗口直接透出桌面），全仓库
>   唯一真实采样点 `ScreenCaptureService.capture(globalDisplayRect:)` 只在鼠标释放

>   **内容刷新**和**位置跟随**拆成两条独立路径：位置跟随（`updateMagnifierPoint`/

>   `CALayer` 属性赋值，零捕获调用；内容采样（`refreshMagnifierSample`）挪到
>   `init` 里启动的独立 80ms 节流 `Task` 循环中，`await` 一次采样失败或变慢只影响
>   放大镜自己画面的新鲜度，永远不会拖慢拖拽响应——用架构上的解耦代替"零延迟"，
>   仍然满足计划本意（拖拽 P95 不受放大镜拖累）。`CaptureOverlayViewDelegate` 新增
>   `didRequestMagnifierSample(globalRect:) async -> CGImage?` 与

>   问题），仍按未验证对待。

## 背景与目标

Lens 的工程质量已经领先同类产品：schema 版本化、G0–G4 发布门、隐私收敛、渲染结果
反向校验、原始素材不可变。功能覆盖也已由两轮竞品调研收敛完毕。

当前与"顶级产品"的差距**全部集中在表现层的手工细节一致性**上，且大部分是
[Lens Glass UI 规范](Lens-Glass-UI规范.md)已经写明、但实现没有落地的条目：

1. **全 App 几乎没有动画**——13 个窗口控制器全部硬切呈现/消失，规范「动效基线」
   要求的"面板出现/消失使用短促弹簧"一行未实现；
2. **设计令牌形同虚设**——`LensGlassMetrics` 定义了 4 个圆角 token，实际代码用了
   19 个野生值；文字字号有 20 种，其中 90 处低于 macOS 系统字体阶梯下限；
3. **用色不克制**——10 种色相在用，`.cyan` 出现 84 次同时充当品牌色、按钮色、
   标签色和选区色，与规范原则 5「克制用色」直接冲突；
4. **没有主次动作**——Quick Access 截图卡 6 个按钮等权等色，库卡片最多 8 个；
5. **成片生成没有进度**——产品里唯一必须等待的环节，信息量最低；
6. **三个签名交互未实现**——录制三秒倒计时、操作中心↔录制控制条形变、多次捕获堆栈，
   全部写在规范里，全仓 grep 结果为 0；
7. **捕获层缺精度工具**——竞品矩阵将 Shottr 的放大镜/取色列为 M3，实际只有 `W × H`。

目标：在不引入任何新依赖、不降低现有测试与发布门槛的前提下，让 Lens 的第一眼观感和
连续使用手感达到 CleanShot X / Raycast / Screen Studio 同档，并把一致性用防回归测试
永久锁死。

**范围决定（2026-08-31）**：国际化不在本轮范围内，界面保持中文硬编码，不引入
String Catalog。本计划所有阶段均无国际化工作项。

## 执行规则（先读完再动手）

1. **先写测试，再改产品代码**。沿用仓库既有的源码文本断言模式
   （`Tests/LensMacTests/*ViewTests.swift`）。
2. **一致性约束用棘轮测试锁死**。新增 `LensDesignTokenLintTests`，扫描
   `Sources/LensMac/UI/` 全目录，对违规数设上限；每个阶段只降不升，最终降到 0
   并把上限改为硬断言。这样中途任何一批都能独立落地，不会回退。
3. **动效绝不进入关键路径**。规范原文：「动效不能延迟剪贴板、保存、录制开始或停止」。
   所有进出场动画必须 fire-and-forget，任何 `await` 动画完成的写法都不允许。
4. **每一批独立可发**。每批结束跑一次目标短回归 + `swift test` 全量，产出
   `docs/功能代码改动记录-*.md`，并按现有流程重新安装构建跑 G4 短时 AX 审计。
5. **不改行为，只改呈现**。任何阶段若发现需要改动 `LensCore`、捕获链或渲染语义，
   停下来单独立项，不混进本计划。
6. **减少动态效果必须全程有效**。所有新动画一律走 `LensMotionPolicy`，
   `accessibilityReduceMotion` 打开时降级为无动画或纯淡入淡出。

## 阶段划分

总量约 15 个工作日，分三批交付。

### P0 设计令牌与防回归门（约 1 天）

**问题**：`LensGlassMetrics` 只有圆角 token，没有字号和间距 token；且没有任何机制
阻止新代码继续写野生值。

**做什么**：

1. `Sources/LensMac/UI/LensGlass.swift` 扩充令牌。

   **关键区分**：`.font(.system(size:))` 在 SwiftUI 里同时用于文字和
   `Image(systemName:)` 的图标尺寸，二者是**两个独立的令牌族**。实测
   UI 目录 263 处 `size:` 中，215 处是文字、48 处是图标。混为一谈会让 lint
   产生大量误报，必须分开定义、分开检查。

   ```
   enum LensType {                     // 文字：6 级阶梯，全部 ≥ 10pt
       static let title    = 15.0      // 窗口/卡片主标题，semibold
       static let body     = 13.0      // 正文与按钮标签
       static let callout  = 12.0      // 次级正文
       static let caption  = 11.0      // 元信息（macOS 正文下限）
       static let micro    = 10.0      // 徽章/标签胶囊，仅限 ≤4 字，semibold
       static let numeric  = 13.0      // 时间码/尺寸，monospaced semibold
   }
   enum LensIcon {                     // 图标：5 级，与字号解耦
       static let small  = 11.0        // 行内状态点、元信息前缀
       static let medium = 13.0        // 按钮内图标
       static let large  = 17.0        // 主操作瓦片、工具条
       static let xlarge = 24.0        // 卡片主视觉
       static let hero   = 34.0        // 空状态、首次启动
   }
   enum LensSpacing { static let xs = 4.0, s = 8.0, m = 12.0, l = 16.0, xl = 24.0 }
   ```

   同时补齐 `LensGlassMetrics` 缺的两档：`badgeCornerRadius = 8`、
   `thumbnailCornerRadius = 10`，使 token 集合能覆盖全部现存合法用法。

2. 新增 `Tests/LensMacTests/LensDesignTokenLintTests.swift`，枚举
   `Sources/LensMac/UI/*.swift`，统计四类违规并与基线上限比较。
   文字/图标的判定方式：向上回溯 3 行，上下文含 `Image(systemName`
   或 `Image(nsImage` 的归为图标，其余归为文字（与本计划实测脚本同规则）。

   | 检查项 | 实测基线（2026-08-31） | 终值 |
   |---|---:|---:|
   | 文字字号不在 `LensType` 内 | **152**（总 215 处 / 20 种取值，其中 <10pt 有 90 处、最小 4pt） | 0 |
   | 图标尺寸不在 `LensIcon` 内 | **48 处待归档**（18 种取值，6.0–36.0） | 0 |
   | `cornerRadius:` 不在 token 内 | **68**（总 92 处 / 19 种取值） | 0 |
   | 系统色字面量 `.cyan/.mint/.indigo/.yellow/.purple/.pink/.teal/.brown` | **102** | 0 |

   基线已实测，直接写入测试常量；每阶段结束后下调，不允许上调。

   **有利事实**：文字字号中 >15pt 的只有 4 处（全部是 16pt），
   因此 5 级文字阶梯无需再加 display 档，4 处并入 `title` 即可。

3. **豁免机制**。纯语法启发式无法完美区分文字与图标——已知反例：
   `LensLibraryView.swift:934` 的 4pt 实为 `LabelStyle` 中的
   `configuration.icon`（一个圆点符号），上下文不含 `Image(systemName`
   却应归为图标。因此 lint 必须支持行内豁免：

   ```
   .font(.system(size: 4))   // lens-token-exempt: LabelStyle 圆点符号，非文字
   ```

   规则：豁免注释**必须带理由**，无理由的裸豁免视为违规；
   lint 同时统计豁免总数并设上限（初始 5），防止用豁免绕过治理。

3. 新增 `Tests/LensMacTests/LensPanelPresentationLintTests.swift`：断言
   `Sources/LensMac/UI/*WindowController.swift` 中不再出现裸的
   `orderFrontRegardless()` / `orderOut(nil)`（P1 完成后启用，P0 先以基线上限形式落地）。
   **例外白名单**：`PinnedImageWindowController`（贴图窗有自己的点击穿透徽章逻辑）
   与 `G4AccessibilityHostRunner`（自建窗口，不经控制器）。

**测试**：`swift test --filter LensMacTests.LensDesignTokenLintTests`——此时应
以基线上限通过（绿），证明棘轮机制本身可用。

**完成判据**：令牌定义落地；两个 lint 测试以当前基线通过；`swift test` 全量不回退。

### P1 浮层动效系统（约 1.5 天）· 收益最高

**问题**：13 个控制器硬切，全 App 仅 5 处动画。这是感知质感的第一杀手。

**做什么**：

1. 新增 `Sources/LensMac/UI/LensPanelPresenter.swift`：

   ```
   @MainActor enum LensPanelPresenter {
       static func present(_ window: NSWindow, from anchor: Anchor = .center)
       static func dismiss(_ window: NSWindow, completion: (() -> Void)? = nil)
   }
   ```

   - 呈现：`alphaValue` 0→1 + `contentView.layer` scale 0.96→1，
     `duration 0.18`，`CAMediaTimingFunction(0.2, 0.9, 0.25, 1)`；
   - 消失：`alphaValue` 1→0 + scale 1→0.97，`duration 0.13`；
   - `anchorPoint` 按锚点设置（Toast 顶部居中、Quick Access 右下角、
     操作中心正中），使缩放从视觉来源方向发生；
   - `NSWorkspace.shared.accessibilityDisplayShouldReduceMotion` 为真时
     直接设 `alphaValue = 1` 并跳过 scale；
   - **必须**先 `orderFrontRegardless()` 再启动动画，保证窗口立即进入层级，
     动画只影响可见性，不影响可用性；
   - `dismiss` 期间若同一控制器再次 `present`，取消进行中的消失动画并复用窗口
     （Quick Access 连拍场景）。

2. 逐个控制器改用 presenter：Toast、Quick Access、操作中心、录制控制条、
   长截图控制条、OCR 结果面板、录屏设置、权限中心、首次启动（9 个）。
   Lens 库、视频编辑器、截图标注器是标准可缩放窗口，**保持系统默认行为不改**。
   贴图窗保持现状（在白名单内）。

3. 捕获遮罩层（`CaptureOverlayWindow`）**明确不加动画**——它必须瞬时出现，
   任何入场动画都会伤害截图手感。这一条写进 lint 白名单并加注释。

**测试**：

- `LensPanelPresenterTests`：`reduceMotion` 为真时 `present` 后 `alphaValue == 1`
  且无进行中动画；连续两次 `present` 不产生窗口泄漏；`dismiss` 中途 `present`

### P6 成片进度（约 1.5 天）

**问题**：`AutoPreviewRenderer` 无进度回调，停止录制后用户面对不确定转圈干等
30–90 秒。竞品已把导出速度当卖点（ScreenKite「快 3 倍」、AutoZoom GPU 4.7×），
而 Lens 已完成的单遍编码优化用户完全感知不到。

**做什么**：

1. `AutoPreviewRenderer.render` 增加可选进度回调：

   ```
   progress: (@Sendable (Double) -> Void)? = nil   // 0...1，按已写帧数 / 总帧数
   ```

   在既有的逐帧循环里按帧计数上报，**节流到最多 10 Hz**，避免高频跨 actor 派发
   影响渲染吞吐。渲染器本身仍不持有 UI 引用。
2. `AudioMixdownRenderer.prepareMixedAudioSidecar` 同样上报，与视频渲染合并为
   两段式总进度（音频 0–15%，视频 15–100%）。
3. `AppDelegate.processRecording` 把进度经 MainActor 转发给
   `QuickAccessWindowController.updateProgress(_:)`。
4. `QuickAccessView` 的不确定 `ProgressView()` 换成确定进度：
   百分比 + 细进度条 + 「约剩 N 秒」（用已用时间与已完成比例线性外推，
   前 10% 不显示预估以免跳变）。
5. 完成瞬间显示一次实际耗时（如「成片已就绪 · 12.4 秒」）——把已有的速度优势
   变成用户可见的产品优势。

**测试**：

- `AutoPreviewRendererTests`：断言进度单调不减、首值 ≥0、末值 ==1、
  节流后回调次数上限合理；断言不传 `progress` 时行为与现状完全一致
  （保护既有调用方）。
- `QuickAccessViewTests`：断言处理态渲染确定进度而非不确定转圈。
- 性能回归：同一段测试录屏，改造前后渲染总耗时差异 <2%（进度上报不得拖慢渲染）。

**完成判据**：进度全链路打通；渲染耗时无可测退化；`swift test` 全量绿。

> **P8 执行结论（2026-08-31）：按计划自身的前置条件暂缓，未实现。**
> 计划原文明确要求"放大镜内容直接取自遮罩层已有的屏幕快照缓存，不新增任何屏幕
> 捕获调用……必须核实现有缓存可复用，否则本阶段暂缓"。实际核查
> `CaptureOverlayWindow.swift`（`backgroundColor = .clear`、`isOpaque = false`）与
> `CaptureOverlayView.swift`（仅有一个 CALayer 蒙版 `regionDimmingLayer` 在选区外
> 画半透明黑色，真实桌面画面直接透过这个透明窗口显示）：遮罩层从未持有过任何屏幕
> 像素缓存，选区之外能看见桌面完全是"窗口透明、系统自己显示桌面"，不是"画了一张
> 截图再叠加暗化"。全仓库唯一的真实屏幕采样点在 `ScreenCaptureService.swift`
> （`SCScreenshotManager.captureImage`），且只在**用户释放鼠标确认选区之后**才调用
> 一次，拖拽过程中完全没有像素数据可读。要做放大镜只能新增一条实时屏幕采样调用，
> 直接违反计划自己写的前提，并且几乎必然打穿同一节列出的拖拽更新 P95 < 3ms 门槛
> （`SCScreenshotManager`/`CGWindowListCreateImage` 单次调用通常是几十毫秒量级，
> 不是亚毫秒量级，装进鼠标移动回调里逐帧调用是不现实的）。这不是绕过一下就能做的
> 事——需要一个本计划未评估过的新采样机制（比如复用录制用的 `SCStream`、或某种
> 更底层的帧缓冲读取方式），风险和范围都超出"UI 质感改造"这一计划本身，因此按计划
> 原文的兜底条款处理：暂缓，不在本计划范围内实现，交由后续单独立项评估。

---

> **P8 补充执行结论（2026-08-31，用户明确要求后重新实现）：已实现，前置条件用
> 不同技术路径满足。**
> 用户在得知"放大镜/取色"功能的实际用途后明确要求"把这两个功能也加上"，构成对
> 上方暂缓决定的明确覆盖。重新核查没有推翻上面的事实认定——`CaptureOverlayWindow`
> 确实没有任何屏幕像素缓存可复用，这一点不成立——但计划原文要保护的其实是"拖拽
> 更新 P95 不被放大镜拖累"这个结果，"复用现有缓存"只是原文设想的**一种**达成
> 手段，不是唯一手段。于是换了另一种手段：把"放大镜内容采样"和"选区位置跟随"
> 从同一条调用路径拆成两条独立路径。位置跟随（指针移动/拖拽时更新放大镜坐标、
> 十字线、CALayer frame）留在 `mouseDragged`/`mouseMoved` 里，全程只有算术和
> `CATransaction`/`CALayer` 属性赋值，不含任何 I/O，因此对同步拖拽耗时的增量
> 成本与"是否有放大镜功能"无关。内容采样（调用
> `ScreenCaptureService.capture(globalDisplayRect:)` 取 9×9pt 区域并解出中心像素
> HEX）挪到 `init` 里启动的独立 `Task` 循环，80ms 节流、顺序执行、`weak self`
> 避免循环引用；对 9×9pt 区域重复采样的临时基准测试显示单次耗时并不稳定
> （多次运行中位数 ~11–12ms，最坏观测到 60–94ms），证实原文"新增一条实时屏幕
> 采样调用几乎必然打穿 P95 门槛"的判断本身没错——但这个判断的前提是"采样调用在
> 拖拽路径上"，把它挪出拖拽路径后，采样有多慢就与拖拽的同步耗时无关了。
>
> 新增 `CaptureOverlayViewTests` 5 项覆盖计划要求的三项断言（放大镜层存在、HEX
> 格式正确、`C` 键复制路径存在）及承载上述性能论证的架构级断言：
> `testMagnifierLayerExistsAndOnlyShowsOncePointerEntersTheOverlay`、
> `testCenterPixelHexReadsBackTheExactRGBBytesAsAnUppercaseTriplet`（纯红/纯蓝
> 精确还原为 `#FF0000`/`#0000FF`，顺带锁死 R/G/B 字节序不被误读成 BGR）、
> `testDraggingNeverSynchronouslyRequestsAMagnifierSample`（连续 50 次拖拽事件
> 全程不让出主线程，断言期间 `delegate.magnifierSampleRequests` 保持为空——
> Swift 并发下新起的 `Task` 不可能抢占当前同步调用栈，这个断言能在不依赖真实
> 计时的前提下确定性地证明拖拽热路径不会同步触发采样）、
> `testPressingCCopiesTheMostRecentMagnifierSampleToThePasteboardAndNotifiesDelegate`、
> `testPressingCBeforeAnySampleDoesNotTouchThePasteboardOrNotifyTheDelegate`。
> 为了让"`C` 键复制"可测，顺手把 `keyDown` 里原先硬编码的 `NSPasteboard.general`
> 改成了 `init` 的可选注入参数（默认值仍是 `.general`，生产调用点不用改），
> 与仓库里 `OCRResultView`/`PinnedImageWindowController` 等所有其余剪贴板写入点
> "可注入 `NSPasteboard`"的一致约定对齐——原先那处硬编码是个孤例，不跟测试就只能
