## 背景与目标

`功能代码改动计划-2026-08-31-UI质感改造.md` 的 P0–P8 已完成，但在其之后追加的
「截图链路玻璃化」需求处于**部分完成**状态，且文档未同步。

关键认知（当晚踩坑得到，写在这里避免重犯）：

1. **Liquid Glass 跟随系统外观**。macOS 26 的 `glassEffect` / `NSGlassEffectView`
   会跟随系统的浅色/深色设置渲染。本机处于深色模式（`defaults read -g
   AppleInterfaceStyle` = `Dark`），因此玻璃材质默认渲染成暗色。
2. **`tint` 压不过深色底**。给玻璃加 `Glass.regular.tint(...)` 只是叠一层色调，
   在深色基底上依然是暗的——这正是当晚三个窗口「改了等于没改」的原因。
3. **真正让玻璃变亮的开关是强制窗口外观**：`window.appearance =
   NSAppearance(named: .aqua)`。这是唯一验证有效的手段（Quick Access 已生效）。
4. **不透明窗口背景会盖掉玻璃**。窗口若设了 `backgroundColor = .windowBackgroundColor`
   （不透明且跟随系统），玻璃层根本透不出来。

目标：把「截图链路上的窗口」在视觉上统一为亮白通透的玻璃质感，用与 Quick Access
同一套、已验证有效的机制；并让文档与代码回到一致状态。

## 执行规则（先读完再动手）

1. **视觉改动必须先装机看效果，再继续下一处**。当晚最大的教训：`NSGlassEffectView`
   被当作可 mask 的普通图层直接用在选区遮罩上，未经目测就装机，结果整屏画面被玻璃
   盖住、截图功能不可用（已回滚，`CaptureOverlayView` 现已确认无残留）。**凡是没法
   用单元测试证明观感的改动，一律装机目测后再推进**，不要连改多处再一起验证。
2. **不猜 API 行为**。macOS 26 的玻璃相关 API 较新，行为以 SDK 头文件/
   `.swiftinterface` 为准（`NSGlassEffectView.h`、`SwiftUICore.swiftinterface` 的
   `struct Glass`），不凭印象写。
3. **强制浅色外观会改变文字/图标的自适应色**。每接一个窗口都要确认其中的固定色
   （如 `.foregroundStyle(.white)`、`.black.opacity(...)` 的角标底色）在浅色底上
   仍然可读，不能只看容器好不好看。
4. **沿用既有令牌与棘轮门**。新加的尺寸/颜色仍走 `LensType`/`LensIcon`/
   `LensGlassMetrics`/`LensGlassPalette`，`LensDesignTokenLintTests` 与
   `LensPanelPresentationLintTests` 只降不升。
5. **每阶段跑全量 `swift test` + Release `-warnings-as-errors` 构建**，与 P0–P8
   同一标准；不得因为「只是改观感」而降低验证等级。

### P1 截图链路玻璃化收尾（约 0.5 天）· 用户当前最关心

**问题**：用户要的「所有截图相关窗口」目前只有 Quick Access 一个真正生效，另外
三处（OCR 结果面板、标注编辑器、画布工具条）用的是深色模式下无效的 `tint`-only 做法。

**做什么**：

1. **OCR 结果面板**（`OCRResultWindowController`）：窗口已是
   `isOpaque = false` + `backgroundColor = .clear`，直接补
   `panel.appearance = NSAppearance(named: .aqua)` 即可，与 Quick Access 同构；
2. **画布工具条**（`ScreenshotCanvasToolbar`）：它嵌在标注编辑器窗口内，随该窗口的
   外观走，**不单独设外观**，由第 3 项覆盖；
3. **标注编辑器**（`ScreenshotAnnotationEditorWindowController`）：需要同时
   （a）设强制浅色外观、（b）处理 `backgroundColor = .windowBackgroundColor` 这个
   不透明背景，否则玻璃透不出来。
   - **这一项需要用户先决策**（见下方「待决策」），因为它是一个完整编辑器窗口，
     不是小浮层，强制浅色的观感影响远大于前两者；
4. 每接一个窗口，按「执行规则 3」检查其中的固定色在浅色底上的可读性；
5. **逐个装机目测**，不要三处一起改完再验证。

**待决策（需用户拍板）**：标注编辑器是整窗强制浅色，还是只让工具条/侧栏玻璃化、
画布区域保持中性？前者视觉最统一但与系统深色模式反差最大，且画布上展示的是用户
自己的截图内容，浅色边框可能影响对内容的判断。

> **决策记录（2026-09-01）**：用户下达「全部执行」后未就此单独回复，遂按其原始
> 表述（「整个 UI 都换成我这个图片的效果」「所有截图相关的窗口」）取**整窗强制
> 浅色**，理由是这最贴合用户明确说出的意图。若目测后觉得画布区域反差过大，回退
> 成本很低：删掉 `ScreenshotAnnotationEditorWindowController` 里那一行
> `applyLensBrightGlassAppearance()` 即可，其余两处不受影响。

**测试**：

- 新增 `LensGlassSurfaceTests`（或并入既有视图测试）：断言 `tint` 与
  `shadowOverride` 参数确实改变了渲染结果（可用现有的快照/渲染断言模式）；
- 新增窗口级断言：截图链路上的各窗口控制器创建出的窗口，其 `appearance` 为
  预期值——这能防止以后有人新增窗口时漏掉，把「只做了 1/4」这个错误棘轮住；
- 既有 `OCRResultViewTests`（10 项）、`ScreenshotAnnotationEditorViewTests`（4 项）、
  `QuickAccessViewTests` 必须继续通过。

**完成判据**：截图链路四个界面在深色模式下均呈现亮色玻璃；上述既有测试不回退；
新增窗口外观断言通过；每一处均已装机目测确认。

### P4 贴图窗口边界钳制（约 0.2 天）

**问题**：`PinnedImageWindowController.swift:165-166` 对每个新贴图窗口先
`center()`、再按 `(窗口数-1) × 28pt` 累加偏移，**没有任何屏幕边界钳制或回绕**。

**做什么**：

1. 落位后按所在屏幕的 `visibleFrame` 钳制，参照同文件角标定位已有的钳制写法；
2. 级联偏移超出可用区域时回绕，而不是无限累加。

**测试**：`PinnedImageWindowControllerTests`（若无则新建）：断言连续钉入 N 张后，
每张窗口的 frame 仍落在某块屏幕的 `visibleFrame` 内。

**完成判据**：连续钉入 10 张贴图后全部可见可点；新增断言通过。

1. **P0 提交检查点**——不产生任何用户可见价值，但它是唯一能防止全盘丢失的动作，不砍；
2. **P1 玻璃化收尾**——用户当前最关心、且目前只完成 1/4，收益最高；
3. **P3 文档同步**——文档失真会让后续任何人（包括未来的我）对完成度产生误判；
4. P2 测试补齐可与 P1 合并执行；
5. P4 贴图钳制是既有缺陷，可按发布节奏安排。
