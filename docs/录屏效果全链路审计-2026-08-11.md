# 屏迹：录屏效果全链路审计

- 日期：2026-08-11
- 范围：既有竞品调研、SPEC、真实 Trace 素材、录制、事件轨、编辑器、预览、导出和重新打开
- 目标：排除“有控件但不生效”、“预览看似成功但仍是旧文件”、“事件与媒体时码错位”和“文档宣称超前”

## 1. 判定方法

一项录屏效果只有同时通过以下链路，才能标为“已实现”：

1. 有可理解的默认值和兼容回退；
2. 控件修改真实写入 `edit-plan.json`；
3. 依赖原始事件的能力会重新规划，不只改配置；
4. 依赖渲染的能力会生成新预览，不只改 SwiftUI 状态；
5. 预览和导出使用同一计划与组合器；
6. 保存、关闭、重新打开后参数不丢失；
7. 媒体中断、超时和渲染失败不得被标记为成功；
8. 至少有模型/规划器回归，高风险视觉效果还要有真实像素或媒体回归。

## 2. 真实素材库快照

本轮只做匿名聚合和结构校验，没有修改用户历史项目。

| 项目 | 结果 |
|---|---:|
| Trace 项目 | 70 |
| 截图 | 47，全部 ready |
| 录屏 | 23（22 ready，1 interrupted） |
| 素材库体积 | 约 1.8 GB |
| 自动预览 | 22 |
| 有点击事件的文件 | 16，344 条事件，其中 161 条 down |
| 有指针事件的项目 | 13，5,045 条 |
| 有窗口事件的项目 | 14，22 条 |

发现的结构异常：

- 1 个 ready 录屏含有可播放的续录分片，但旧分片索引没有持久化时长，最终成片只包含第一段；
- 3 个历史计划含有超过成片时长的点击波纹；
- 4 个历史计划含有超过成片时长的光标关键帧；
- manifest 与当前 `raw/screen.mp4` 时长未发现其他超过 50 ms 的不一致。

这说明用户看到的“自动运镜没了”不一定只是曲线调参问题：如果点击发生在被旧逻辑遗漏的续录分片中，那些点击对当前成片本来就不可见。

## 5. 本轮修正

1. 自动倍率、点击推近、跟随光标和生成强度不再只改配置，会重读事件并重新生成自动镜头。
2. 光标、点击、运动模糊、音频和字幕控件在提交修改后自动重新渲染，无须再猜测是否点了保存。
3. 预览渲染后必须确认 manifest 回到 `ready`，否则不再将模型标记为“已保存”，也不会把旧 `auto.mp4` 当作新预览。
4. 停止录制时逐段读取真实可播视频时长，可播但未写入时长的分片不再被静默丢弃。
5. 分片麦克风和摄像头轨按对应屏幕分片时长裁齐，防止屏幕流意外结束后侧轨继续增长导致同步偏移。
6. 自动计划在生成前过滤成片时长之外的点击和指针事件，不再生成不可见效果。
7. 新增可播但未完成分片恢复、事件越界过滤、音频裁齐、视频侧轨裁齐和画布阴影回归。
8. 修复参数变化后退回原始媒体导致“倍率一调就没有自动跟进”的假失效：原始媒体预览现在按播放源时间实时应用镜头缩放、平移和边缘约束；完整重新编码继续在后台执行，并明确区分事件分析与预览生成阶段。

## 8. 发布结论

当前不能因为“控件已经出现”就宣布录屏效果完成。本轮已关闭主要假链路和一个实际分片丢失类型，但 Beta 发布状态仍是：

> 代码链路已接通，351 项自动回归全部通过；真机长流程、故障注入和盲测仍是发布闸门。

本轮还通过了 Release warnings-as-errors 构建、App 深度签名验证和 201 个跟踪文件的公开源审计。新 Release App 已重启，操作中心和录屏工作台的只读界面冒烟通过，前置摄像头仍默认关闭。公开发布仍被 LICENSE 决策阻塞。

## 9. 2026-08-12 调参生效复核

- 再次逐项核对编辑器控件到 `AutoEditPlan`、项目落盘、后台预览和最终导出的完整链路；倍率、生成强度、点击推近、光标跟随、运动模糊、光标与波纹、画布、人像、字幕、时间线和三档导出均由真实规划器或渲染器消费，不存在只改变界面数值的占位控件。
- 复核发现并修复一个条件性空链路：录屏只有系统声、没有麦克风轨时，系统音量此前不会进入混音器。现在非 1.0 的系统音量会触发系统声单轨混音；0.25 的参数通过真实媒体峰值验证约为原始值的 25%。
- 导出仍以当前内存中的最新方案为准；存在未生成修改时，导出会先原子落盘并重新生成，再复制 MP4，不会导出旧 `auto.mp4`。
- 全量自动化更新为 381 项通过、0 失败；Release 构建、严格签名、安装校验和单实例重启通过。安装构建为 `0.1.0 (20260812100034)`。

## 10. 2026-08-12 最终编码媒体反事实门

之前的健康报告能够证明事件轨、镜头计划和效果参数存在，但“计划存在”仍不能证明效果已经进入最终 MP4。本轮增加以下发布证据链：

1. 从最终 `auto.mp4` 解码实际输出帧；
2. 从 raw 的对应源时间解码原始帧；
3. 使用同一组合器生成仅切换一项效果的“开启/关闭”反事实帧；
4. 只在两份反事实真实变化的像素上比较编码帧误差；
5. 分别记录变化像素、预期差异、开启误差、关闭误差和相似度增益；
6. 同时读取 raw 与 preview 的实际样本时间，验证“原画/平衡/轻量”的帧率门槛；
7. 结果落入 `diagnostics/recording-health.json`。失败或无法判定时不再显示“效果已完成”，编辑器导出也会要求先重渲染并通过验证。

真实 Trace 复核结果：

| 素材 | 自动运镜 | 光标 | 点击反馈 | 画布 | 帧率 |
|---|---:|---:|---:|---:|---:|
| 历史 `2560×1480 / 35.85 s` 成片 | 通过 | **失败** | 通过 | 通过 | 平衡档 30.06 FPS，通过该档门槛 |
| 当前代码临时重渲染（未改原项目） | 通过 | **通过，增益 0.982** | 通过 | 通过 | 30.06 FPS，通过该档门槛 |

根因不是光标轨为空，而是旧尺寸规则在 Retina 源上生成的重绘光标过小。实时预览与最终渲染现共用 `1.8%` 源宽、32–96 px 边界的尺寸函数，再乘用户倍率；新增 2560 px 真实编码后缩放回归。完整自动化更新为 `408 tests / 0 failures`。

本轮 Release 构建、深度签名、覆盖安装、版本/可执行哈希校验和单实例启动均通过；已安装构建为 `0.1.0 (20260813003841)`，上一构建保留为可恢复备份。

## 11. 2026-08-12 音频、原始轨与长录屏证据

- 摄像头画中画和字幕现使用与最终组合器一致的反事实帧进行验证，不再以“有轨道/有文本”代替成片证据。
- 音频混音从最终 MP4 解码首、中、尾 5 组 PCM 窗口，记录输出 RMS、参考 RMS、PCM 差异和音视频时长偏差。系统声 0.25× 成片实测通过，未调节的原片冒充成片会被判失败；系统声 + 麦克风混音也通过最终 PCM 差异验证。
- `recording-health.json` schema 升至 `0.3`，保存屏幕、系统声、麦克风和摄像头物理轨时长；请求轨缺失或相对屏幕轨偏差超过 `150 ms` 会进入健康警告和用户收尾提示。
- 长视频停止路径不再遍历排序全部帧；30 秒内仍全量验证，更长视频有界解码首/中/尾 5 个真实媒体窗口。编码器动态帧积压限制为 8 帧，静止补帧最多保留 2 秒共用像素缓冲，防止 4K 长录屏内存无界增长。
- 系统录屏流意外结束时，若 AVAssetWriter 能正常封口，App 现会自动安全收尾并保留中断前原片；只有写入器自身失败才进入中断恢复。
- G2 安装版视频冒烟报告位于 `Build/Quality/g2-recording-stress-installed-60s.json`：2560×1664 / 60 FPS，实际 60.000 秒，实测 60.0 FPS，P95 16.67 ms，0 丢帧，停止到可播放 128.3 ms，峰值物理内存 83,247,872 bytes。
